# Arquitetura da MetricsFlow AI

## 1. Visão geral

A **MetricsFlow AI** é uma aplicação de gestão financeira que permite organizar empresas, categorias e movimentações financeiras, com recursos de inteligência artificial para auxiliar no processamento de informações financeiras.

A arquitetura é dividida em:

- **Frontend:** aplicação web desenvolvida com Next.js, React e TypeScript.
- **Backend:** API REST desenvolvida com NestJS e TypeScript.
- **Autenticação:** Supabase Auth, incluindo suporte ao login com Google.
- **Banco de dados:** PostgreSQL disponibilizado pelo Supabase.
- **Inteligência artificial:** módulo responsável por coordenar o processamento de informações financeiras.
- **WhatsApp:** módulo com funcionalidades de demonstração e estrutura preparada para integração com a API oficial.
- **Armazenamento de arquivos:** camada relacionada aos anexos das movimentações, cuja configuração e integração devem corresponder à implementação efetiva do projeto.

## 6. Fluxo de autenticação e acesso

O Supabase Auth gerencia a identidade e a sessão do usuário. A aplicação associa os usuários às empresas por meio dos registros de participação, respeitando os papéis e as permissões implementados.

```mermaid
flowchart TD
    A["Usuário acessa a MetricsFlow AI"] --> B["Frontend inicia autenticação"]
    B --> C["Supabase Auth"]
    C --> D{"Autenticação concluída?"}
    D -- "Não" --> E["Exibe erro ou mantém o usuário na autenticação"]
    D -- "Sim" --> F["Frontend obtém a sessão"]
    F --> G["Usuário acessa a aplicação"]
    G --> H["Frontend envia requisição à API"]
    H --> I["Backend verifica autenticação e autorização"]
    I --> J{"Acesso permitido?"}
    J -- "Não" --> K["Retorna resposta de acesso negado"]
    J -- "Sim" --> L["Executa a operação solicitada"]
    L --> M["Retorna os dados ao frontend"]
```

O fluxo acima é uma representação conceitual. As verificações exatas dependem dos guards, da validação de tokens, das políticas de acesso e das regras de negócio implementadas.

## 7. Fluxo de movimentações financeiras

O fluxo geral de movimentações envolve o frontend, a API, as regras de autorização e a persistência dos dados.

```mermaid
sequenceDiagram
    actor Usuario as Usuário
    participant FE as Frontend
    participant API as Backend NestJS
    participant AUTH as Autenticação e autorização
    participant DB as Supabase PostgreSQL

    Usuario->>FE: Solicita operação financeira
    FE->>API: Envia requisição REST
    API->>AUTH: Verifica identidade e permissões
    AUTH-->>API: Resultado da validação

    alt Acesso autorizado
        API->>DB: Consulta ou altera dados
        DB-->>API: Resultado da operação
        API-->>FE: Resposta HTTP com os dados
        FE-->>Usuario: Atualiza a interface
    else Acesso negado
        API-->>FE: Resposta de erro de acesso
        FE-->>Usuario: Apresenta o resultado
    end
```

## 8. Fluxo de inteligência artificial

O módulo de IA deve coordenar as solicitações feitas pelo backend a um provedor externo. O provedor e os modelos utilizados precisam corresponder às configurações reais do projeto.

```mermaid
sequenceDiagram
    actor Usuario as Usuário
    participant FE as Frontend
    participant API as Backend NestJS
    participant AI as AIModule
    participant PROVIDER as Provedor de IA

    Usuario->>FE: Envia informação financeira
    FE->>API: Solicita processamento
    API->>AI: Encaminha os dados
    AI->>PROVIDER: Solicita interpretação ou transcrição
    PROVIDER-->>AI: Retorna o resultado
    AI-->>API: Entrega o resultado processado
    API-->>FE: Retorna a resposta
    FE-->>Usuario: Exibe o resultado
```

### 8.1. Configuração do provedor

Caso a integração com a Groq esteja implementada, o diagrama pode identificar explicitamente o provedor:

- **Provedor:** Groq API.
- **Credencial:** chave de API armazenada em variável de ambiente.
- **Modelo financeiro:** definido pela configuração utilizada no serviço.
- **Modelo de transcrição:** definido pela configuração utilizada no serviço.

As variáveis de ambiente devem corresponder ao código que lê essas configurações. Alterar o nome de uma variável não altera automaticamente o provedor usado pela aplicação.

## 10. Arquitetura de anexos das movimentações

Os anexos podem envolver duas responsabilidades distintas:

1. **Banco de dados:** armazena os metadados e a referência do arquivo.
2. **Armazenamento de objetos:** guarda o conteúdo binário do arquivo, caso exista um serviço de storage configurado.

O diagrama abaixo representa essa separação de responsabilidades. O serviço de armazenamento e os relacionamentos só devem ser considerados implementados depois de confirmar a configuração e o código.

```mermaid
flowchart TD
    A["Usuário solicita acesso aos anexos"] --> B["Frontend"]
    B --> C["Backend NestJS"]
    C --> D["Verifica autenticação e permissão"]
    D --> E{"Acesso permitido?"}
    E -- "Não" --> F["Retorna erro de acesso"]
    E -- "Sim" --> G["Consulta metadados do anexo"]
    G --> H["Banco de dados"]
    H --> I["Obtém a referência do arquivo"]
    I --> J{"Storage configurado e integrado?"}
    J -- "Não" --> K["Retorna apenas os dados disponíveis"]
    J -- "Sim" --> L["Obtém o arquivo ou gera acesso conforme a política"]
    L --> M["Retorna o resultado ao frontend"]
```

### 10.1. Considerações sobre anexos

- A existência de uma tabela `attachments` não comprova, por si só, que o upload e o download de arquivos estejam implementados.
- O nome do bucket, as políticas de acesso, os tipos de arquivo aceitos e os limites de tamanho devem ser documentados a partir da configuração real.
- O acesso aos anexos deve respeitar as permissões da empresa e da movimentação associada.
- Se o conteúdo for armazenado em Supabase Storage, documente o bucket e suas políticas separadamente do esquema relacional.

## 11. Estrutura lógica do banco de dados

O banco de dados utiliza PostgreSQL no Supabase. Entre as entidades relacionadas à aplicação estão usuários, empresas, membros, categorias e movimentações financeiras.

O diagrama abaixo é uma visão simplificada. Ele não substitui o esquema real do banco, e as cardinalidades e os nomes das chaves devem ser conferidos com as migrations ou definições atuais.

```mermaid
erDiagram
    COMPANIES ||--o{ COMPANY_MEMBERS : possui
    USERS ||--o{ COMPANY_MEMBERS : participa
    COMPANIES ||--o{ TRANSACTIONS : registra
    CATEGORIES ||--o{ TRANSACTIONS : classifica
    TRANSACTIONS ||--o{ ATTACHMENTS : possui

    USERS {
        uuid id PK
    }

    COMPANIES {
        uuid id PK
    }

    COMPANY_MEMBERS {
        uuid user_id FK
        uuid company_id FK
        string role
    }

    CATEGORIES {
        uuid id PK
    }

    TRANSACTIONS {
        uuid id PK
        uuid company_id FK
        uuid category_id FK
    }

    ATTACHMENTS {
        uuid id PK
        uuid transaction_id FK
    }
```

> **Atenção:** esse ERD é conceitual e inclui apenas campos mínimos para representar as relações. Antes de tratá-lo como documentação definitiva, confira os nomes reais das tabelas, as chaves estrangeiras, os campos obrigatórios e a existência da tabela `users`. Se o identificador do usuário for gerenciado diretamente pelo Supabase Auth, o relacionamento pode apontar para a tabela de usuários do schema `auth`, em vez de uma tabela pública chamada `users`.

## 12. Princípios arquiteturais

- **Separação de responsabilidades:** interface, API, persistência e integrações externas possuem responsabilidades distintas.
- **Organização modular:** o backend utiliza módulos NestJS para agrupar funcionalidades.
- **Autorização por contexto empresarial:** as operações devem considerar a empresa e as permissões do usuário.
- **Integrações desacopladas:** provedores externos devem ser acessados por serviços específicos.
- **Segurança:** credenciais e chaves privadas devem permanecer no backend ou em configurações seguras.
- **Documentação fiel à implementação:** diagramas, endpoints e integrações devem ser atualizados quando o código mudar.
